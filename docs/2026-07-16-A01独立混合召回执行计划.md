## 1. 计划目标

A-01 的根因不是 ES BM25 算法本身，而是当前实现只让 ES 在 Dense 已召回的 `chunk_id` 集合内打分。ES 因此只是 Dense 候选的重排器，无法独立召回 Dense 漏掉但关键词高度相关的分块。

本计划将检索链路调整为：

```text
权限范围解析
  ├─ Dense / Milvus 独立召回
  └─ Sparse / Elasticsearch BM25 独立召回
             ↓
        chunk_id 去重并集
             ↓
       Weighted RRF 融合
             ↓
      DB 权威校验与信息补全
             ↓
   可选 Cross-Encoder 重排（Flat）
             ↓
           Top K
```

执行完成后必须满足以下验收目标：

1. ES 查询不再携带 Dense 候选的 `chunk_ids` 过滤条件。
2. Dense 未命中、ES 命中的分块可以进入融合候选集，并有机会进入最终 Top K。
3. Dense 与 ES 的原始分数不直接线性相加，统一使用基于名次的 Weighted RRF。
4. ES 返回的分块必须通过数据库中的 `DocumentChunk`、`File.deleted_at`、工作区和权限范围校验后才能返回。
5. 权限范围解析异常时必须失败关闭，不能退化成“搜索所有文件”。
6. 文件重新处理时，ES 必须先按 `file_id` 删除旧文档再写入新文档，并检查完整写入数量。
7. 历史 ES 数据先执行只读一致性审计；只有发现孤儿、缺失或归属错误时，才定向清理或重建，不做无条件全量重建。
8. Flat 与 Contextual 两条链路都具备独立 Sparse 召回能力。
9. Trace 能区分 Dense、Sparse、融合、DB 过滤和重排各阶段，并能统计 Sparse 独立挽回的结果。
10. 现有搜索 API 结构保持兼容；`vector_similarity_weight` 字段保留，但语义变为“Dense 通道的名次融合权重”。

## 2. 已确认的边界与决策

### 2.1 本次必须实现

- 独立 ES BM25 召回接口。
- Dense 与 Sparse 候选集并集。
- Weighted RRF 融合。
- 权限范围显式化和失败关闭。
- DB 权威校验、软删除过滤、归属校验和批量信息补全。
- Flat 与 Contextual 两条检索链路接入。
- ES 重处理前删除旧文档、写入数量检查。
- 历史 ES 索引只读审计和按结果处置。
- Trace、离线评测、灰度开关和回滚能力。

### 2.2 本次不扩大处理

- 不调整 Embedding 模型、切块算法、Query Rewrite、HyDE 或 ES analyzer。
- 不把 Contextual 链路的 Cross-Encoder 重排统一问题并入 A-01；该问题单独立项。
- 不新增数据库表或数据库字段；现有 `DocumentChunk`、`File` 和 Trace JSON 字段足以支撑本次修复。
- 不把文件删除链路改造成强事务；删除期间 ES 暂时不可用产生的残留由 DB 读时校验兜底，并由一致性审计发现。
- 第一版不并发执行 Dense 与 Sparse 查询，先保证正确性；只有性能验收不通过时再单独优化并行调用。
- 第一版不允许“管理员全局搜索”直接向 ES 发无文件范围的查询。无法得到有限、已验证的 `file_id` 集合时跳过 Sparse，保留 Dense 结果并记录原因。

### 2.3 历史数据处置结论

如果历史数据只经历过“上传 → 删除 → 再次上传”，没有发生同一 `file_id` 的重新解析或分块更新，并且删除时 ES 可用、删除请求成功，则一般不会出现旧分块残留。

但不能只凭业务操作记录证明 ES 一定一致，因为历史删除是 best-effort，ES 暂时不可用、超时或部分失败都可能留下残留。因此执行顺序是：

1. 先完成读时 DB 权威校验，确保错误 ES 文档不能成为最终结果。
2. 再修复未来重新处理时的 delete-before-upsert 和完整写入检查。
3. 对现有索引执行一次只读审计。
4. 审计结果为零异常时不重建；仅对发现异常的工作区或文件定向处理。

## 3. 模块边界和接口原则

本次实现遵循“外部接口稳定、内部模块加深”的原则：

- 对调用方继续保留 `RetrievalService.search()` 作为主检索接口。
- `EsChunkStore` 作为 ES Adapter，只负责索引读写和把 ES hit 转成统一的 Sparse hit。
- 新增纯计算内部模块 `hybrid_fusion.py`，只负责候选归并与 Weighted RRF，不访问数据库、ES 或 Milvus。
- `RetrievalService` 负责编排权限范围、两个召回通道、融合、DB 校验和 Trace。
- `search_api.py` 只负责请求解析、服务构造、可选 Reranker 和响应格式化，不承载融合算法。
- 不新增一个与 `RetrievalService` 平级、只转发调用的浅层 `HybridRetrievalService`。

统一内部 hit 字段约定如下：

| 字段 | 来源 | 含义 |
|---|---|---|
| `chunk_id` | Dense / Sparse | 分块唯一标识，也是两路结果去重键 |
| `file_id` | Dense / Sparse / DB | 文件标识，最终以 DB 校验结果为准 |
| `text` | Dense / Sparse | 候选文本；最终结果需要通过 DB 存在性校验 |
| `dense_score` | Dense | Milvus 原始相似度，仅用于诊断，不直接与 BM25 相加 |
| `sparse_score` | Sparse | ES 原始 BM25 `_score`，仅用于诊断，不直接与 Dense 分数相加 |
| `dense_rank` | 融合模块 | Dense 通道内从 1 开始的名次，未命中为 `null` |
| `sparse_rank` | 融合模块 | Sparse 通道内从 1 开始的名次，未命中为 `null` |
| `fused_score` | 融合模块 | Weighted RRF 分数，只表示候选融合排序依据 |
| `reranked_score` | Reranker | Cross-Encoder 的最终重排分数；只有真正执行重排后才允许写入 |
| `recall_sources` | 融合模块 | `dense`、`sparse` 或二者，用于诊断和统计 |
| `retrieval_mode` | RetrievalService | `flat` 或 `contextual` |

## 步骤 1：把检索权限范围改为显式状态，并在解析失败时关闭访问

### 在做什么

本步骤将权限解析结果改为显式对象，区分：

- 已验证的有限文件集合。
- 已验证的管理员全局范围。
- 权限解析失败。
- 业务过滤后为空集合。

### 可以解决什么问题

- 消除权限异常时 fail-open 的高危行为。
- 为 ES 独立查询提供明确、可审计的文件范围。
- 防止 `None`、空集合和管理员全局三种语义混用。

## 步骤 2：修复未来文件重新处理时的 ES 写入一致性

### 在做什么

当前文件重新解析时，Milvus 会先按 `file_id` 删除旧向量，但 ES 只执行 bulk upsert。如果新分块数量减少或 chunk ID 发生变化，旧 ES 文档可能残留。本步骤把 ES 写入改为：

```text
ensure index
  → delete_by_file_id(file_id)
  → bulk_upsert_chunks(new_docs)
  → 校验 upsert_count == new_doc_count
  → 记录成功、部分成功或失败
```

### 可以解决什么问题

- 防止同一文件重新处理后旧 chunk 残留在 ES。
- 防止 bulk 部分失败却被当成完整成功。
- 为后续独立 Sparse 召回消除最主要的新增脏数据来源。

### 影响范围

| 类型 | 文件 | 函数 / 类 | 字段 / 事件 |
|---|---|---|---|
| 修改 | `openrag/src/openrag/processors/document_processor.py` | 文档处理流程中的 ES Step 5a | `file_id`、`chunk_id`、`workspace_id`、`workspace_slug`、`content`、`es_doc_count`、`es_upsert_count`、`es_failure_reason`；新增 `es_delete_performed`、`es_write_complete` |
| 复用 | `openrag/src/openrag/search/es_chunk_store.py` | `delete_by_file_id()`、`bulk_upsert_chunks()` | ES `_id=chunk_id`、`file_id` |
| 修改测试 | `openrag/tests/test_document_processing_trace.py` | `FakeEsStore`；ES 操作顺序和部分写入测试 | `operations`、`doc_count`、`upsert_count`、`failure_reason` |

本步骤不修改 `File`、`DocumentChunk` 数据库表结构，也不要求 ES 与数据库形成分布式事务。

### 实施要点

1. `delete_by_file_id()` 必须发生在 `bulk_upsert_chunks()` 之前。
2. `bulk_upsert_chunks()` 返回值必须与 `len(es_docs)` 比较；少写一条也应标记 `es_write_complete=false`。
3. ES 故障不能破坏当前 Dense 可用性，但必须留下可观测的失败状态，供重试或审计发现，不能只打印笼统 warning。
4. 空分块文件也要执行旧 ES 文档删除，避免旧数据残留。
5. 不改变现有文档处理成功状态语义；是否把 ES 部分失败升级为任务失败，应单独评估，A-01 先采取“Dense 可用 + Sparse 明确降级”的策略。

### 如何验证

```powershell

pytest -q tests/test_document_processing_trace.py
```

测试必须覆盖：

- 重新处理同一 `file_id` 时，Fake ES 记录的调用顺序严格为 delete 后 bulk。
- 新文档数从 5 减到 3 后，ES 最终只存在 3 个新 `chunk_id`。
- bulk 返回 2/3 时，`es_write_complete=false` 且 `es_failure_reason` 可定位部分写入。
- ES 不可用时 Dense 处理仍完成，但 Trace 明确 Sparse 不完整。
- 新分块为空时旧 ES 文档被删除。

### 完成标准

- 未来同一文件重处理不会因为 chunk ID 变化留下旧 ES 文档。
- 部分写入不再被记录成成功。
- 不新增数据库迁移。

## 步骤 3：建立历史 ES 索引只读一致性审计和条件处置流程

### 在做什么

### 可以解决什么问题

- 识别删除时 ES 不可用造成的孤儿文档。
- 识别处理失败或 bulk 部分失败造成的 ES 缺失文档。
- 给定向清理或重处理提供具体工作区、文件和 chunk 清单。

## 步骤 5：新增纯 Weighted RRF 融合模块

### 在做什么

新增不依赖数据库、Milvus、ES 和 Web 框架的纯计算模块，将 Dense 和 Sparse 排名列表按 `chunk_id` 做并集并使用 Weighted Reciprocal Rank Fusion 排序：

```text
fused_score(d) = w_dense / (k + rank_dense(d))
               + w_sparse / (k + rank_sparse(d))
```

第一版固定 `k=60`，`w_dense=vector_similarity_weight`，`w_sparse=1-w_dense`。

### 可以解决什么问题

- 避免不同量纲的 cosine similarity 与 BM25 原始分数直接线性相加。
- 让任一通道独立命中的 chunk 都进入候选集。
- 让融合算法可独立测试、可解释且结果确定。

### 影响范围

| 类型 | 文件 | 函数 / 类 | 字段 / 参数 |
|---|---|---|---|
| 新增 | `openrag/src/openrag/retrieval/hybrid_fusion.py` | `weighted_rrf()`；内部候选规范化/稳定排序辅助函数 | `chunk_id`、`dense_score`、`sparse_score`、`dense_rank`、`sparse_rank`、`fused_score`、`recall_sources`、`dense_weight`、`rrf_k`、`limit` |
| 新增测试 | `openrag/tests/test_hybrid_fusion.py` | 并集、去重、权重边界、稳定排序、重复 chunk、输入不变性测试 | 同上 |

### 实施要点

1. 去重键只能是 `chunk_id`，不能使用文本或 `file_id + chunk_index`。
2. 输入列表名次从 1 开始；没有命中某通道时该通道贡献为 0。
3. Dense 与 Sparse 原始分数只保留为诊断字段，不参与 RRF 公式。
4. 权重必须满足 `[0, 1]`；Sparse 权重为 `1 - dense_weight`。
5. 权重为 0 的通道不参与候选并集：`dense_weight=1` 时只保留 Dense 候选，`dense_weight=0` 时只保留 Sparse 候选，避免零贡献候选依靠 tie-break 混入结果。
6. 相同 `fused_score` 使用确定性的 tie-break：优先最小最佳名次，再按 `chunk_id`，保证重复执行结果一致。
7. 函数不修改调用方传入的列表和字典。
8. RRF 分数不能命名为 `similarity` 或解释成概率。

### 如何验证

```powershell

pytest -q tests/test_hybrid_fusion.py
```

关键断言：

- Dense=[A,B,C]、Sparse=[D,A] 的输出集合是 A/B/C/D。
- D 具有 `sparse_rank` 且没有 `dense_rank`，不会在融合前丢失。
- A 只出现一次，并同时保留两个通道分数和名次。
- 改变 BM25 原始分数绝对值但不改变名次时，RRF 排序不变。
- 输入顺序、相同分数和重复 chunk 的行为确定且可复现。

### 完成标准

- 融合模块是纯函数，单元测试不需要启动任何外部服务。
- 并集、权重、去重和稳定排序均有测试覆盖。
- 未引入新的公共服务层。

## 步骤 6：以数据库为权威校验融合候选并批量补全结果

### 在做什么

ES 是检索索引，不是权限和生命周期的权威来源。融合后的候选必须批量查询数据库，确认 chunk 和文件仍然有效、归属正确且在已解析权限范围内，再补全文件名、URI、页码等返回字段。

### 可以解决什么问题

- 消除现有 `_enrich_hits()` 中逐条查询 File 的 N+1 问题。

## 步骤 8：在 Contextual 检索链路中接入独立 Sparse 召回

- 防止 L0 Dense 未选中文件时，关键词明确的 Sparse 结果永远没有机会出现。

## 步骤 9：补齐分阶段 Trace、诊断统计和离线评测

### 在做什么

把原先含义模糊的 `retrieval.es_fusion` 拆成可区分的 Dense 召回、Sparse 召回、融合、DB 过滤和 Reranker 阶段，并复用现有 EvalService 比较新旧链路。

### 可以解决什么问题

- 可以证明 Sparse 是否真的独立贡献，而不是只改变 Dense 排序。
- 可以发现 ES 残留、越权候选、部分索引缺失和降级率。
- 为灰度放量和回滚提供可量化依据。

### 影响范围

| 类型 | 文件 | 函数 / 类 | 字段 / 指标 |
|---|---|---|---|
| 修改 | `openrag/src/openrag/retrieval/retrieval_service.py` | `_search_flat()`、`_search_contextual()`、`_recall_sparse()`、`_merge_independent_recalls()`、`_validate_and_enrich_hits()` | Trace stage：`retrieval.dense_recall`、`retrieval.sparse_recall`、`retrieval.hybrid_fusion`、`retrieval.db_validation`；计数见下文 |
| 复用/必要时小改 | `openrag/src/openrag/services/trace_service.py` | `start_span()`、`finish_span()`、`record_snapshot()` | 复用现有 `score_parts`、`metadata_` JSON，不新增列 |
| 修改测试 | `openrag/tests/test_retrieval_trace.py` | 阶段、计数、失败原因和 score_parts 断言 | `dense_count`、`sparse_count`、`union_count` 等 |
| 修改评测 | `openrag/tests/fixtures/a01_retrieval_eval.json` | 扩充人工相关性标注，并通过 `EvalService.import_dataset()` 导入 | `query_type`、`judgments[].chunk_id/file_id/relevance_grade/source`、查询分类 metadata |
| 复用 | `openrag/src/openrag/services/eval_service.py` | 现有默认搜索与指标计算 | `Recall@K`、`MRR@50`、`nDCG@K`、`stage_recall@50` |

### 必须记录的统计

| 指标 | 含义 |
|---|---|
| `dense_count` | Dense 召回数 |
| `sparse_count` | Sparse 召回数 |
| `overlap_count` | 两路共同命中的 chunk 数 |
| `dense_only_count` | 仅 Dense 命中的 chunk 数 |
| `sparse_only_count` | 仅 Sparse 命中的 chunk 数 |
| `union_count` | 去重并集候选数 |
| `stale_sparse_hit_count` | ES 命中但 DB 无有效 chunk/file 的数量 |
| `unauthorized_sparse_hit_count` | ES 命中但不在权限范围内的数量，正常应为 0 |
| `ownership_mismatch_count` | ES 与 DB 文件或工作区归属不一致数量 |
| `sparse_rescued_final_count` | 仅 Sparse 命中且最终进入 Top K 的数量 |
| `sparse_degraded` | ES 是否降级 |
| `sparse_skip_reason` | 权重为 1、全局范围、禁用、超时等原因 |
| 各阶段 `latency_ms` | Dense、Sparse、融合、DB 校验、Reranker 耗时 |

### 实施要点

1. 每个候选的 `score_parts` 保存原始分数、名次和融合贡献，但不记录超出权限范围的正文。
2. `sparse_rescued_final_count` 是 A-01 最关键的效果指标；如果长期为 0，需要检查召回范围、融合权重或评测集。
3. EvalService 沿用现有指标，不另造一套不兼容的评测框架。
4. 新旧模式在同一评测集上分别运行，结果按查询类型拆分，不能只看总体均值。
5. 性能至少记录 p50、p95；如果 p95 超过门槛，先分析 ES 与 DB 阶段，再决定是否并行召回。

## 步骤 10：统一 API、前端和文档中的权重与分数语义

### 在做什么

保留 API 字段名以避免破坏兼容性，但修改描述和前端文案，明确 `vector_similarity_weight` 控制的是 Dense 通道在 RRF 中的贡献，而不是 Dense 原始分数与 BM25 原始分数的线性比例。

### 可以解决什么问题

- 避免用户把 RRF 分数理解为相似度或概率。
- 避免融合逻辑写入 `reranked_score`，导致调用方误判已经执行 Cross-Encoder。
- 让 API、UI、代码和运维配置的描述一致。

| 修改 | `web/src/pages/Search.tsx` | 搜索参数表单和帮助提示 | `vector_similarity_weight`、默认值 `0.7`、“向量通道权重” |

### 实施要点

1. 不改 API 字段名和 JSON 结构，默认值暂时保留 `0.7`，实际最优默认值由评测决定。
2. 响应 `score` 的兼容选择顺序固定为：

4. UI slider 的 0 和 1 分别解释为纯 Sparse 排名贡献和纯 Dense 排名贡献。
5. 如果产品不希望开放极端权重，可在后续产品评审处理，不在 A-01 中偷偷改变请求校验范围。

## 7. 关键风险及控制措施

| 风险 | 可能后果 | 控制措施 |
|---|---|---|
| 权限范围仍用 `None` 混合语义 | 独立 ES 查询越权 | 步骤 1 必须先完成；异常 fail-closed；ES 只接受有限列表 |
| ES 历史残留 | 返回已删除内容 | DB 读时校验先上线；只读审计；按报告定向处置 |
| RRF 权重语义误解 | 排名调参失控 | 保留原字段名兼容，但统一 API/UI/文档解释；原始分数不参与公式 |

| 长期保留 legacy | 双实现漂移 | 设置观察期和删除门槛，步骤 11 明确清理 |
| 无条件重建 ES | 造成停机或数据丢失 | 默认 dry-run 审计；零异常不处理；大面积问题使用新索引回填切换 |
