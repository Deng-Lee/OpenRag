# A-01 独立混合召回修复方案

> 日期：2026-07-16  
> 范围：仅修复 A-01“ES/BM25 不能独立召回，只能给向量候选重打分”的问题；本文不落实代码。

## 1. 结论

推荐将当前链路从：

```text
Milvus 召回 -> ES 在 Milvus chunk_id 范围内打分 -> 线性融合
```

调整为：

```text
Milvus 独立召回 ─┐
                  ├─ 按 chunk_id 求并集 -> Weighted RRF -> 可选 Cross-Encoder -> Top K
ES BM25 独立召回 ─┘
```

修复应同时覆盖平面检索和分层检索。分层检索中，ES 必须面向完整授权文件范围独立召回，不能继续受 L0 候选文件或 L2 向量候选限制。

上线前必须先解决 ES 旧 chunk 残留问题：文档重处理时先按 `file_id` 删除旧 ES 文档，再写入新 chunk；同时对独立召回结果执行 DB 权威校验。否则独立 ES 召回会把此前隐藏的索引垃圾直接带入结果集。

## 2. 假设与边界

### 2.1 假设

1. `chunk_id` 是跨存储稳定且全局唯一的候选合并键；当前 PostgreSQL 已对 `DocumentChunk.chunk_id` 设置唯一约束。
2. PostgreSQL 中的 `DocumentChunk` 与 `File` 是 chunk 是否仍然有效、文件是否已软删除的权威来源。
3. Elasticsearch 是可选依赖；ES 不可用时系统继续退化为向量检索。
4. 现有 `vector_similarity_weight` 暂时保留，避免立即破坏 Web 和 API 请求兼容性。
5. 第一版不调整 ES analyzer、不做查询改写、不改 chunking；这些属于其他准确率问题。

### 2.2 非目标

- 不同时引入 SPLADE、ColBERT、HyDE、多查询改写等新能力。
- 不重构整个 `RetrievalService`。
- 不修改知识库权限模型。
- 不把 RRF 参数、候选窗口等全部暴露成用户配置。
- 不把 RRF 分数解释为概率或余弦相似度。

## 3. 当前问题的代码根因

当前 `_search_flat()` 和 `_search_contextual()` 都先产生向量候选，然后调用 `_blend_elasticsearch_scores()`。

`_blend_elasticsearch_scores()` 从向量候选中提取 `chunk_ids`，调用：

```python
self.fulltext_store.search_chunk_scores(
    index_names=index_names,
    query_text=query,
    file_ids=filter_file_ids,
    chunk_ids=chunk_ids,
)
```

而 `EsChunkStore.search_chunk_scores()` 的 ES 查询包含：

```json
{"ids": {"values": ["向量候选 chunk_id"]}}
```

所以当前 ES 的角色是“候选内重打分器”，不是“召回器”。任何未进入 Milvus Top N 的 chunk 都没有进入后续融合和重排的机会。

分层路径的问题更严重：L0 先用向量摘要筛文件，L2 再用向量筛 chunk，ES 最后只处理这些 L2 chunk。关键词精确命中文件可能在 L0 就被排除。

## 4. 目标架构与模块职责

### 4.1 保持外部 interface 不变

继续以 `RetrievalService.search()` 作为调用方和测试使用的主要 interface。API 层不需要了解 Dense、Sparse 的执行顺序、去重和融合细节。

不建议新增一个与 `RetrievalService` 平级、只做转发的公开 `HybridRetrievalService`。双路召回编排应作为 `RetrievalService` 的内部实现，保证复杂度集中和调用方稳定。

### 4.2 Elasticsearch adapter

在 `EsChunkStore` 增加一个独立召回 interface：

```python
def search_chunks(
    self,
    *,
    index_names: list[str],
    query_text: str,
    file_ids: list[int],
    top_k: int,
) -> list[dict]:
    ...
```

返回项至少包含：

```python
{
    "chunk_id": str,
    "file_id": int,
    "text": str,
    "sparse_score": float,
}
```

实现要求：

- 删除 `ids` 限制；
- 保留授权 `file_ids` 过滤；
- `size=top_k`；
- 只返回 `_source` 中的 `file_id`、`content`，将 `content` 映射为统一的 `text`；
- `_id` 作为权威 `chunk_id`，并校验 `_source.file_id` 可转换为整数；
- 缺少 `index_names`、`file_ids` 或查询为空时返回空结果，不能执行无范围全文检索。

大文件范围不能直接假设 ES 的 `terms` 查询永远可容纳全部 `file_ids`。adapter 内部应按安全批次拆分 file scope，对每批取 Sparse Top N，再按原始 BM25 分数合并为全局 Top N；该细节不能泄漏给 `RetrievalService` 调用方。

`ResolvedFileScope(None)` 只代表经过验证的管理员全局检索，绝不能被解释成“ES 不加过滤”。第一版建议对此路径跳过 Sparse 并退化为 Dense，记录 `admin_global_sparse_unsupported`；后续若确有需求，再通过枚举授权工作区索引和有效文件范围实现独立 Sparse，而不是发送无范围查询。指定 `workspace_id` 的管理员检索仍会得到明确的有效文件列表，不受此限制。

旧的 `search_chunk_scores()` 在灰度期保留给 legacy 路径；新链路稳定后删除，避免长期维护两个含义相近的 interface。

### 4.3 内部融合模块

新增一个纯计算内部模块，例如：

```text
openrag/src/openrag/retrieval/hybrid_fusion.py
```

只暴露一个小 interface：

```python
weighted_rrf(
    dense_hits,
    sparse_hits,
    *,
    dense_weight,
    rrf_k=60,
) -> list[dict]
```

该模块负责：

- 按 `chunk_id` 去重；
- 保留 Dense/Sparse 原始分数与各自排名；
- 计算 Weighted RRF；
- 生成稳定排序；
- 标记候选来源 `dense`、`sparse` 或 `dense+sparse`。

不要在该模块里访问 DB、Milvus、ES 或环境变量，使其保持纯函数并可直接测试。

### 4.4 权威校验与补全

当前 `_enrich_hits()` 只补字段，不会删除 ES 中已经失效的 chunk。独立召回上线后，应将其调整或旁路增加为“批量校验并补全”：

1. 一次查询候选 `chunk_id` 对应的 `DocumentChunk`；
2. 一次查询相关 `File`；
3. 删除不存在于 `DocumentChunk` 的候选；
4. 删除 `DocumentChunk.file_id` 与命中 `file_id` 不一致的候选；
5. 删除不在 `ResolvedFileScope` 内的候选；
6. 删除 `File.deleted_at IS NOT NULL` 的候选；
7. 补齐 filename、uri、页码、位置、对象存储路径等字段。

必须使用批量查询，不能继续对每个 hit 单独查询 `File`，否则候选并集扩大后会放大 N+1 查询。

## 5. 融合算法

### 5.1 为什么不继续使用原始分数 min-max 线性融合

Milvus cosine 与 ES BM25 的分数分布没有可比性；而每次查询在小候选集上做 min-max，会受极值和候选数量强烈影响。独立召回后两个通道的分数分布差异会更加明显，因此不建议继续使用：

```text
w * minmax(cosine) + (1-w) * minmax(BM25)
```

### 5.2 Weighted RRF

建议使用：

```text
score(c) =
    dense_weight / (rrf_k + dense_rank(c))
  + (1 - dense_weight) / (rrf_k + sparse_rank(c))
```

候选未出现在某一路时，该路贡献为 0。`rrf_k` 第一版固定为 60，不暴露给请求接口。

字段建议：

```python
{
    "dense_score": 0.82,       # 原始 Milvus 分，仅观测
    "sparse_score": 12.7,      # 原始 BM25 分，仅观测
    "dense_rank": 4,
    "sparse_rank": 1,
    "fused_score": 0.0213,     # 用于融合后排序
    "recall_sources": ["dense", "sparse"],
}
```

排序稳定规则：

1. `fused_score` 降序；
2. 两路都命中的候选优先；
3. 最佳单路排名升序；
4. `chunk_id` 升序，保证结果可复现。

### 5.3 `vector_similarity_weight` 的兼容策略

第一版继续把它作为 Dense 通道权重：

- `1.0`：仅 Dense，不访问 ES；
- `0.0`：Sparse 排序为主；
- `0~1`：Weighted RRF；
- 默认值暂时保持 `0.7`，避免在没有离线评测结果前静默改变线上行为。

该参数从“原始分数线性权重”变为“排名通道权重”，需要同步修改接口说明和 Web 提示。

不建议立即增加 `dense_top_n`、`sparse_top_n`、`rrf_k` 等公开参数。先沿用当前候选预算：平面检索使用调用方传入的候选 `top_k`，分层检索使用现有 `fetch_k`，Sparse 与对应向量侧使用相同召回深度。

## 6. 两条检索路径的具体改造

### 6.1 平面检索

目标流程：

```text
ResolvedFileScope
  ├─ Milvus.search(top_k=N, file_ids=授权范围)
  └─ ES.search_chunks(top_k=N, file_ids=同一授权范围)
                ↓
         两路分别做授权兜底过滤
                ↓
              RRF 并集
                ↓
          DB 权威校验与补全
                ↓
       返回候选给现有 Cross-Encoder
```

调整点：

- `_search_flat()` 不再先 enrich Dense 再请求 ES；应在两路合并后统一校验和 enrich；
- 替换 `_blend_elasticsearch_scores()`，不再传 Dense `chunk_ids` 给 ES；
- `use_rerank=True` 时，现有 API 已按 `top_k * 3` 获取候选，合并后的候选全部交给 reranker，再裁剪到用户 `top_k`；
- `use_rerank=False` 时，按 RRF 排序后裁剪。

### 6.2 分层检索

将整个 L0/L1/L2 向量管线视为 Dense/Contextual 通道，将 ES 视为独立 Sparse 通道：

```text
L0/L1/L2 向量管线得到 contextual_hits ─┐
                                        ├─ RRF 并集 -> 校验 -> Top K
完整授权范围 ES BM25 得到 sparse_hits ──┘
```

关键约束：

- ES 的 `file_ids` 必须来自完整 `ResolvedFileScope`，不能使用 `candidate_files`；
- Sparse-only 候选允许绕过 L0 文件筛选，否则 A-01 在分层路径仍未修复；
- L1 LLM 导航只约束 Contextual 通道，不删除 Sparse-only 精确命中；
- Sparse-only 候选没有 L0/L1 分数是正常情况，由 RRF 与后续重排处理；
- 最终结果仍执行 DB 权威校验，防止 ES 孤儿 chunk 或软删除文件进入响应。

当前上下文检索路径没有真正调用 `Reranker`。这不是 A-01 的必要修复条件，建议作为紧随其后的独立任务，把“候选召回”和“最终 rerank/裁剪”统一放到 API 编排层，避免在本次修复中扩大改动面。

## 7. ES 索引一致性前置修复

### 7.1 重处理先删后写

当前 `DocumentProcessor` 对 Milvus 会先 `delete_by_file_id()`，但 ES 只 bulk upsert。若新旧 chunk_id 不一致，旧 ES 文档会残留。

在 `bulk_upsert_chunks()` 前增加：

```text
delete_by_file_id(index_name, file_id)
-> bulk_upsert_chunks(index_name, current_docs)
-> 校验成功写入数与 current_docs 数一致
```

删除成功、写入失败时，该文件暂时只有 Dense 结果，优于返回旧全文内容。ES 仍作为可降级依赖，不应把在线文件的主处理状态错误地标记为向量不可用，但必须记录可重试的全文索引失败。

### 7.2 既有索引处理

仅修复未来写入不够。启用独立召回前，应完成一次工作区 ES 全量重建或孤儿文档清理，并核对：

- ES chunk 总数与当前有效 `DocumentChunk` 数量；
- ES `_id` 是否全部能在 PostgreSQL 找到；
- `file_id`、`workspace_id` 是否与 PostgreSQL 一致；
- 软删除文件是否仍有 ES 文档。

如果无法立即全量重建，至少必须先上线 DB 权威校验，并对 ES 召回做适度 oversampling，避免 Top N 被孤儿文档占满；但这只应作为过渡方案。

## 8. 失败与降级语义

| 场景 | 行为 |
|---|---|
| ES 未启用/初始化失败 | 返回 Dense 结果，记录 `no_fulltext_store` |
| ES 查询超时/异常 | 返回 Dense 结果，记录 `sparse_error` 与耗时 |
| Dense 查询失败 | 保持现有语义，搜索请求失败；不要静默伪装成完整混合检索 |
| ES 返回越权 file_id | 丢弃并记录安全告警 |
| ES 返回 DB 不存在的 chunk | 丢弃并记录 `stale_sparse_hit_count` |
| 授权范围为空 | 不调用 Milvus/ES，直接返回空结果 |
| `vector_similarity_weight=1` | 跳过 ES |
| `vector_similarity_weight=0` 且 ES 失败 | 为保持现有可用性，退化为 Dense，并明确标记 degraded |

所有降级都不能扩大授权范围。

## 9. 可观测性

将当前 `retrieval.es_fusion` 拆成更清晰的阶段：

- `retrieval.dense_recall`
- `retrieval.sparse_recall`
- `retrieval.hybrid_fusion`
- 保留已有 `retrieval.rerank`

建议记录：

- `dense_count`
- `sparse_count`
- `union_count`
- `overlap_count`
- `dense_only_count`
- `sparse_only_count`
- `stale_sparse_hit_count`
- `unauthorized_sparse_hit_count`
- `sparse_rescued_final_count`
- Dense/ES/融合/重排各阶段耗时
- fusion method、权重、候选窗口

快照中记录原始分数、排名和融合分，不记录 chunk 正文。`sparse_rescued_final_count` 定义为最终 Top K 中只由 Sparse 通道召回的有效 chunk 数，是验证 A-01 是否真正修复的关键指标。

## 11. 分阶段实施顺序

### 阶段 0：建立基线

- 建立包含精确关键词查询的评测集；
- 记录 legacy Recall@10、MRR、nDCG、p95；
- 从 trace 确认当前 `sparse_only_count` 恒为 0。

验收：能够稳定复现“ES 全局能命中、Milvus Top N 漏掉、最终无结果”的 A-01 样例。

### 阶段 1：先修 ES 一致性

- 文档重处理先删旧 ES chunk，再写当前 chunk；
- 增加 DB 权威校验；
- 清理或全量重建既有 ES 索引。

验收：独立抽查的 ES 命中全部能映射到有效 `DocumentChunk` 和未删除 `File`。

### 阶段 2：实现独立 Sparse adapter 与 RRF

- 增加 `search_chunks()`；
- 增加纯 RRF 模块及单元测试；
- legacy 方法暂时保留。

验收：无需启动 Milvus，即可通过 fake adapter 验证 Sparse-only 候选进入融合结果。

### 阶段 3：接入平面检索

- `_search_flat()` 改为双路独立召回；
- 合并后统一校验/enrich；
- 保持现有 reranker 与 API 最终 Top K 行为。

验收：A-01 平面回归测试通过；ES 故障时结果与 legacy Dense 基线一致。

### 阶段 4：接入分层检索

- Contextual 向量结果与完整授权范围 Sparse 结果做 RRF；
- 验证目标文件不在 L0 候选时仍可由 Sparse 救回；
- L1 LLM 不过滤 Sparse-only 候选。

验收：分层 A-01 回归测试、路径 scope、软删除、权限测试全部通过。

### 阶段 5：灰度与收口

- 通过临时配置 `legacy|independent_rrf` 灰度；
- 对比离线指标、Sparse rescue、ES 错误率和 p95；
- 达标后默认启用 independent RRF；
- 稳定期结束后删除 legacy `_blend_elasticsearch_scores()` 和 `search_chunk_scores()`。

验收：删除 legacy 前，至少连续一个观察周期无权限回归、无明显 p95 回退，且精确查询 Recall 明显提升。

## 12. 上线门槛

必须同时满足：

1. Dense 漏召回、Sparse 独立命中的自动化用例通过；
2. 分层路径中 Sparse 能绕过 L0 文件漏召回；
3. 权限、路径 scope、软删除测试全部通过；
4. ES 孤儿 chunk 不会进入最终响应；
5. ES 故障可退化为 Dense；
6. 评测集 Recall@10 不低于 legacy，精确标识符子集 Recall@10 有明确提升；
7. nDCG@10、MRR@50 不超过现有 quality gate 允许的回退；
8. p95 延迟不超过既定阈值；若超标，再将 Dense/ES 两个远程查询并行化，不在正确性实现中提前增加并发复杂度。
