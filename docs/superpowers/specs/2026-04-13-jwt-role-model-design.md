# 增加基于 JWT 的角色模型设计

## 1. 需求与目标
在现有系统基础上，为 OpenRag 增加一套基于角色的权限控制体系。
核心诉求包括：
1. **自定义角色**：支持自定义角色名称、`role_code` (纯英文和下划线，用户输入系统唯一)、是否启用（`is_active`），以及配置每个角色对各项目空间（Workspace）的读写权限。
2. **账号授权**：可对账号授予角色，一个账号可拥有多个角色。账号将自动继承其所拥有角色对项目空间的读写权限。
3. **取消授权即时生效**：角色与账号之间的关联可以取消，取消后对应的权限立刻失效。
4. **权限页面重构**：修改 `[权限]` 页面，展示当前账号拥有的所有角色及其在各项目空间的读写权限。展示时需标明权限来源（例如：是某个角色赋予的，还是单独授予的）。

## 2. 架构设计

考虑到系统复杂度和未来扩展，本功能采用**方案：关系型严格建模**与**方案：JWT仅作身份标识，后端实时鉴权**。
这保证了数据的强一致性，并满足“权限更改立刻生效”的需求。

### 2.1 数据模型设计

在后端新增 3 个核心数据模型（存放于 `src/openrag/models/role.py` 或合适位置）：

#### Role (角色表)
- `id`: Integer, 主键
- `name`: String, 角色名称 (显示用)
- `role_code`: String, 角色编码 (纯英文和下划线，用户输入，系统级唯一标识，用于辨认)
- `is_active`: Boolean, 是否启用 (默认 True)
- `description`: String, 角色描述 (可选)
- `created_at`, `updated_at`: 时间戳

#### RoleWorkspacePermission (角色-项目空间权限表)
- `id`: Integer, 主键
- `role_id`: Integer, 外键关联 `Role.id`
- `workspace_id`: Integer, 外键关联 `Workspace.id`
- `permission`: String, 权限级别 (`read` 或 `write`)

#### UserRole (账号-角色关联表)
- `id`: Integer, 主键
- `user_id`: Integer, 外键关联 `User.id`
- `role_id`: Integer, 外键关联 `Role.id`

*(保留现有的 `WorkspaceMember`，它将专门用于记录对账号“单独授予”的项目空间权限。)*

### 2.2 鉴权与权限计算逻辑 (后端)

- **JWT Token**: JWT payload 保持原样，只包含 `sub` (`user_id`)，以作为身份凭证。
- **权限拦截计算 (取并集 - 最高权限)**: 
  当用户访问某个项目空间 API 时，后端的 `WorkspaceService` (或相关权限拦截器) 将通过查询数据库或缓存来实时计算权限：
  1. 查询该用户单独被授予的权限（`WorkspaceMember`）。
  2. 查询该用户绑定的所有**已启用** (`is_active=True`) 的角色 (`UserRole` -> `Role`)。
  3. 查询这些角色对目标空间的权限 (`RoleWorkspacePermission`)。
  4. 最终权限取所有来源的并集（即最高权限）：只要有一方授权了 `write`，则具有写权限；否则如果有 `read`，则具读权限；否则拒绝访问。

**失效机制**: 当取消账号角色授权（删除 `UserRole`）或禁用角色（`is_active=False`）时，由于每次请求都会走上述实时计算，角色附带的权限会在下一次请求时**立刻失效**。

### 2.3 `[权限]` 页面改造 (前端+后端API)

- **前端展示原则**: 权限页面**不合并**不同来源的权限记录，而是要向用户如实展示其拥有的**每一条具体授权记录**。
- **页面数据结构**:
  - 当前账号关联的所有角色列表（包含 `role_code`、名称、是否启用等）。
  - 当前账号拥有的项目空间权限列表。列表项不仅包括空间名称和读写权限级别，还**必须包含来源标识**。
- **展示示例**: 
  - 对于某个项目空间 A，页面可能呈现出多条记录：
    - 空间A - 读 - (来源：单独授予)
    - 空间A - 写 - (来源：角色: 管理员 / `admin_role`)
    - 空间A - 读 - (来源：角色: 观察者 / `viewer_role`)
- **API 改造**: 提供一个新的（或修改现有的）API 端点 `/users/{user_id}/permissions/details`，返回一个包含单独授权 (`WorkspaceMember`) 和所有角色授权 (`UserRole` -> `RoleWorkspacePermission`) 及其关联角色名称/code 的完整明细列表。

## 3. 约束与检查清单 (Self-Review)
- **占位符**: 无。
- **内部一致性**: 鉴权时取并集以确保功能正常（最高权限生效），但在页面展示时拆分展示不同来源，这二者逻辑自洽且能避免权限来源混淆。
- **范围控制**: 设计明确限定在增加 Role 模型及对现有 Workspace 权限逻辑的适配，没有过度重构。
- **歧义性**: 明确了 `role_code` 的命名规则（纯英文和下划线）及唯一性约束。明确了失效机制是通过后端实时查库（而非依赖 JWT 刷新）。
