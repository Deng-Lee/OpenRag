## 1. 目标

A02 本轮只实施以下五项能力：

1. 严格 Elasticsearch Mapping。
2. `exact_terms` 精确标识符检索。
3. 继续使用当前 `content` BM25 作为全文检索主通道。
4. 版本化索引与 Trace。
5. 一致性审计、迁移和回滚基础设施。

实施后的检索链路为：

```text
标题与正文融合后的 chunk.text
  ├─ 原文 → content（Elasticsearch standard analyzer / BM25）
  └─ 规则抽取 → exact_terms（keyword）
                    ↓
          严格 Mapping 的 workspace v2 索引
                    ↓
     content BM25 + exact_terms 高权重精确命中
                    ↓
              A01 Weighted RRF
                    ↓
           DB 权限与有效性校验
                    ↓
        Trace、评测、审计与可回滚结果
```

完成后必须满足：

1. v2 索引设置 `dynamic: strict`，未知字段无法写入。
2. `content` 继续使用 BM25，现有自然语言全文检索行为不被替换。
3. 标准号、型号、错误码和配置项可通过 `exact_terms` 稳定命中。
4. Mapping、物理索引和查询规则均有版本记录。
5. 新文档和历史回填文档使用同一个文档构造入口。
6. v2 建立在新物理索引上，不原地修改 v1。
7. 切换前可以审计，切换后可以原子回滚。
8. A01 的独立 Sparse 召回、权限边界、DB 校验和 Weighted RRF 不被破坏。

## 2. 实施范围与明确排除项

### 2.1 本轮实施

| 能力 | 本轮结论 |
|---|---|
| 严格 Mapping | 实施完整字段契约、`dynamic: strict`、本地写前校验和 Mapping hash |
| 全文检索 | 继续检索融合后的 `content`，使用 ES `standard` analyzer 和 BM25 |
| 精确标识符 | 新增 `exact_terms: keyword[]`，文档和查询共用规范化/抽取函数 |
| 查询规则 | `content` 为主通道，`exact_terms` 作为高权重精确通道 |
| 索引版本 | 使用 v2 物理索引、读别名、写别名和原子切换 |
| Trace | 记录索引版本、Mapping hash、查询规则版本、命中通道和 Sparse 排名 |
| 历史数据 | 从 DB 与 L2 权威正文幂等回填 v2 |
| 运维安全 | 提供 dry-run 审计、切换前校验和 alias 回滚 |

### 2.2 本轮明确不实施

- 不引入任何新的中文分词依赖。
- 不新增中文词法分析模块。
- 不生成、不写入、不查询 `content_ltks`、`content_sm_ltks`。
- 不生成、不写入、不查询 `mom_ltks`、`mom_sm_ltks`。
- 不使用正文粗粒度 `2.0`、正文细粒度 `1.0` 的双通道权重。
- 不使用基于分词数量的动态 `minimum_should_match`。
- 不记录 `tokenizer_version`，因为本轮没有自定义 tokenizer。
- 不启用或补齐 `OPENRAG_CHILDREN_DELIMITER` 的父子检索能力。
- 不区分标题与正文；继续使用已经融合的 `chunk.text`。
- 不改变切块算法、Embedding 模型、Dense 召回、Weighted RRF 或 Reranker。
- 不新增数据库表或数据库字段。
- 不删除 v1 索引。

如果未来重新实施中文粗细粒度分词，必须使用新的 Schema 和查询规则版本，并重新构建物理索引，不能直接向本轮 v2 动态增加字段。

## 3. 模块划分与唯一接口

本轮只增加一个负责索引契约的深模块，不再增加分词器模块。

| 模块 | 职责 | 不负责 |
|---|---|---|
| `openrag.search.es_chunk_contract` | 定义字段和版本；构造 Mapping；规范化/抽取 exact term；构造并校验 ES 文档；计算 Mapping hash | 不发 ES 请求、不查询数据库、不编排召回 |
| `EsChunkStore` | 作为 ES Adapter 创建和校验索引、执行 bulk、执行 content/exact 查询、解析 hit、管理 alias | 不重新定义字段语义、不实现权限判断 |
| `DocumentProcessor` | 把 chunk、file、workspace 信息交给契约模块，再写入 write target | 不手工拼接 ES 文档、不处理 exact 正则 |
| `RetrievalService` | 解析权限范围、调用 A01 Sparse 召回、融合、DB 校验和记录 Trace | 不知道 exact 抽取规则和 Mapping 细节 |
| 迁移与审计脚本 | 从 DB/L2 重建 v2、比较 DB/ES 集合、验证版本、切换或回滚 alias | 不重新切块、不改变 chunk ID |

`es_chunk_contract` 的外部接口控制为以下最小集合：

```python
build_chunk_mapping() -> dict
compute_mapping_hash() -> str
extract_exact_terms(text: str) -> list[str]
build_chunk_search_document(...) -> dict
validate_chunk_search_document(document: dict) -> None
```

接口约束：

1. 所有 v2 文档必须经过 `build_chunk_search_document()`。
2. 文档 builder 内部调用 `extract_exact_terms()`，调用方不能自行传入一套不同规则。
3. `bulk_upsert_chunks()` 只接受通过契约校验的文档。
4. `EsChunkStore` 从契约模块取得 Mapping 和版本，不维护第二份字段列表。
5. 测试通过同一接口验证 Mapping、文档构造和 exact term，不穿透测试内部正则。

## 4. v2 字段契约与查询规则

### 4.1 严格 Mapping

v2 索引顶层设置：

```json
{
  "dynamic": "strict"
}
```

允许写入的完整 `_source` 字段如下：

| 字段 | ES 类型 | 写入来源 | 消费位置与作用 |
|---|---|---|---|
| `chunk_id` | `keyword` | `chunk.chunk_id` | ES `_id`、Dense/Sparse 去重、DB 校验、Trace |
| `file_id` | `long` | `File.id` | 授权文件过滤、按文件删除、DB 归属校验 |
| `workspace_id` | `long` | `Workspace.id` | 索引归属审计和迁移校验 |
| `workspace_slug` | `keyword` | 规范化后的 workspace slug | 索引归属审计和排障 |
| `content` | `text`，`analyzer: standard`，`search_analyzer: standard` | 标题与正文融合后的 `chunk.text` | v2 全文检索主通道和 Sparse hit 文本 |
| `doc_type_kwd` | `keyword` | `chunk.metadata.doc_type_kwd`，缺省 `text` | 文档类型审计；本轮不参与排序 |
| `content_with_weight` | `text`，`index: false` | 与 `content` 相同的兼容原文 | 保留当前 RAGFlow 兼容字段，不参与检索 |
| `mom_with_weight` | `text`，`index: false` | 当前 metadata 中已有值；没有则为空 | 只兼容现有写入，不派生 token、不参与检索 |
| `exact_terms` | `keyword` 多值字段 | 从 `content` 抽取并规范化 | 精确标识符召回和加权 |
| `schema_version` | `keyword` | 契约常量 | 单文档 Schema 审计 |
| `mapping_hash` | `keyword` | 稳定 Mapping SHA-256 | 检测文档、代码和实际索引是否一致 |

v2 不允许出现：

```text
content_ltks
content_sm_ltks
mom_ltks
mom_sm_ltks
title_ltks
title_sm_ltks
tokenizer_version
```

上游 chunk metadata 即使仍包含旧 token 字段，`build_chunk_search_document()` 也必须忽略它们。未知字段如果绕过 builder 进入 bulk，本地校验和 ES strict Mapping 都必须拒绝。

### 4.2 索引 `_meta`

索引 `_meta` 固定记录：

```json
{
  "schema_version": "a02-content-exact-v2",
  "mapping_hash": "<canonical-mapping-sha256>",
  "query_profile_version": "a02-content-exact-v1",
  "content_analyzer": "standard"
}
```

`mapping_hash` 对不含 `_meta.mapping_hash` 自身的规范化 Mapping 计算，使用稳定键排序和 JSON 序列化。

### 4.3 exact term 规则

文档与查询使用同一个 `extract_exact_terms()`。首版规则：

1. 全角字符转半角。
2. 英文字母统一小写。
3. 去除首尾空白并压缩内部空白。
4. 保留标识符内部的 `-`、`_`、`.`、`/`。
5. 只保留含字母或数字且具有标识特征的片段。
6. 按首次出现顺序去重。
7. 单项最长 128 字符，每个 chunk 最多 64 项。
8. 不把普通自然语言整句写入 `exact_terms`。

首批必须覆盖：

- `GB/T 35273-2020`
- `HT-2025-001`
- `Qwen3-Embedding-0.6B`
- `OPENRAG_RETRIEVAL_USE_L0_L1`
- 版本号、错误码和带斜杠的标识符

### 4.4 查询规则

`a02-content-exact-v1` 只包含两个通道：

| 通道 | 字段 | boost | 说明 |
|---|---|---:|---|
| 全文 | `content` | 1.0 | 继续使用 ES standard analyzer 与 BM25 |
| 精确标识符 | `exact_terms` | 8.0 | 查询能抽取出 exact term 时加入 |

DSL 规则：

1. `content` 使用当前 `multi_match`/`match` 语义，不增加自定义分词和动态匹配比例。
2. `exact_terms` 使用结构化 `terms`/`term` 查询，不拼接 Lucene query string。
3. 两个通道放入 `should`，`minimum_should_match=1`。
4. 查询没有 exact term 时，只执行 `content` BM25，行为与当前主通道保持一致。
5. `file_ids` 仍作为 A01 提供的有限授权过滤。
6. query 为空或授权文件集合为空时直接返回空结果，禁止 `match_all`。
7. 使用 named query：`content_bm25`、`exact_identifier`。

## 步骤 2：实现 exact_terms 同源规范化与抽取

### 在做什么

- 避免标准号、型号和错误码被普通全文分析拆散。

- 避免文档侧和查询侧使用不同正则导致无法精确相交。

### 影响范围

| 类型 | 文件 | 函数 | 字段 |

## 步骤 3：建立 v2 物理索引、别名和路由配置

### 在做什么

现有无版本后缀的 `openrag_ws_{segment}_chunks` 视为逻辑 v1 并保持不变；新建：

```text
openrag_ws_{segment}_chunks_v2
openrag_ws_{segment}_chunks_read
```

### 8.2 必须停止推进

出现以下任一情况时不得进入下一阶段或切换 alias：

- v2 Mapping hash 与代码期望不一致。
- v2 写入出现未知字段或 token 字段。
- exact 文档侧和查询侧规范化结果不一致。
- 回填 workspace 存在 L2 缺失、DB/ES 集合不一致或部分 bulk 失败。
- v2 请求缺少有限、已验证的 `file_ids`。
- A01 权限、软删除或 DB 归属校验回归。
- 普通 content 查询明显低于 v1 基线。
- alias 无法原子切换或无法回滚。
