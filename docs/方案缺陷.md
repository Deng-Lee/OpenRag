# OpenRag 文档类型分块方案的当前缺陷

本文总结 OpenRag 在接入 `document_type` 并对标 RAGFlow 的 `general`、`manual`、`laws` 分块能力时，当前方案中暴露出的两个核心缺陷，以及这些缺陷产生的原因。

## 问题一：`heading/level` 没有被妥善用于 chunk 组织

OpenRag 当前已经在部分 parser 中生成了结构化的 `DocumentBlock` 信息。例如 DOCX 和 Markdown 解析时，可以将标题识别为：

```text
block_type = "heading"
level = 1 / 2 / 3 ...
```

这些字段说明 parser 已经捕获到了一部分文档结构，但当前默认的 semantic chunk 流程并没有稳定地把它们作为章节组织规则来使用。

当前 semantic chunk 主要依据以下信息组织 chunk：

```text
文本内容
chunk_size
delimiter
overlap
table/image 特殊处理
```

`heading/level` 更多只是被携带到 `DocumentBlock` 或最终 `Chunk` 的字段、metadata 中，并没有稳定承担以下职责：

```text
标题作为 section 起点
标题和下属正文组成完整 chunk
同级或更高级标题结束当前 section
按标题层级维护章节边界
```

因此，一个标题不一定会和其下属正文组成完整 chunk；也可能因为 chunk 的起始位置不同，最终 chunk 是否继承标题的 `level` 具有偶然性。

## 产生原因一：semantic 当前缺少 sectionizer 逻辑

当前 `ragflow_core.semantic` 在处理普通文本类 block 时，基本会把 `heading` 和普通 `text` 一样放入文本合并流程。

也就是说：

```text
heading block
normal text block
paragraph block
```

在 semantic merge 阶段都会被视作文本片段，而不是结构边界。

同时，当前 chunk 在生成时会根据文本范围找到它覆盖到的 `DocumentBlock`，并取第一个覆盖到的 block 作为 owner。这个 owner 会影响最终 chunk 的：

```text
page
bbox
level
block_type
source_block_id
```

这种做法能保留来源信息，但它不能表达真正的章节结构。如果 chunk 从标题开始，它可能继承标题的 `level`；如果 chunk 从正文开始，即使它语义上属于某个标题下的章节，也可能只继承正文的 `level=0`。

根本原因是当前没有一个显式的 sectionizer 来表达：

```text
遇到 heading level=1/2/3 时开启一个 section
将标题后的正文、表格、图片归入该 section
遇到同级或更高级标题时结束当前 section
再将 section 交给后续 chunk merge
```

因此，`DocumentBlock` 中已有的结构信号没有被充分消费。

## 问题二：通用 `DocumentBlock` 对 manual/laws 的结构表达能力有限

当前 OpenRag 的主流程是：

```text
parser_type -> DocumentBlock[] -> Chunk[]
```

其中 `parser_type` 负责选择文件格式解析器，例如 `auto`、`pdf`、`docx`、`txt`；`DocumentBlock` 是 parser 的统一输出；`ChunkEngine` 再将这些 block 组织成最终 chunk。

这个结构对统一多种文件格式很有价值，但当前 `document_type` 尚未进入 parser 阶段，因此 parser 在生成 `DocumentBlock` 时，并不会因为用户选择了 `manual` 或 `laws` 而改变解析方式。

以 PDF 为例，当前 PDF `DocumentBlock` 通常可以携带：

```text
page
bbox
line_positions
block_type = text/table
char_start / char_end
```

但它不一定能可靠表达：

```text
标题层级
法规条款层级
章/节/条之间的父子关系
手册步骤结构
页眉页脚噪声过滤结果
复杂版面下的真实阅读顺序
```

因此，如果后续只在 chunk 阶段根据 `document_type` 做 `manual/laws` profile，能够利用的原料主要还是已有文本、坐标和少量 block 类型。对于结构清晰的文本型文档，这可以改善 chunk；但对于复杂 PDF、扫描 PDF、双栏排版、页眉页脚混杂、条款跨页等场景，chunk profile 只能靠文本规则补救，效果上限会受限于 `DocumentBlock` 的质量。

## 产生原因二：当前 parser 阶段未根据 `document_type` 优化 block 生成

RAGFlow 的 `manual`、`laws` 并不是单纯的 chunk 策略。它们更像是“解析 + 分块”的一体化模块。

在 RAGFlow 中，`manual/laws` 可以在多个阶段同时针对文档类型优化：

```text
PDF layout recognizer
sections 生成
title level 判断
目录过滤
条款/编号识别
tree_merge
tokenize_chunks
```

也就是说，RAGFlow 的 `manual/laws` 能够更早介入 PDF 结构识别过程，而不是等到通用 parser 产出普通文本块后再补救。

当前 OpenRag 为了统一多格式解析结果，引入了 `DocumentBlock` 中间层。这本身不是问题，反而是 OpenRag 保持统一处理链路的关键设计。但目前的问题在于：

```text
document_type 只计划进入 chunk 阶段
尚未进入 parser 阶段
PDF parser 未根据 manual/laws 产出更高质量的 DocumentBlock
```

因此，OpenRag 当前的 `DocumentBlock` 更像是通用解析结果，而不是针对 `manual/laws` 优化过的结构化结果。

## 结论

当前问题不在 `DocumentBlock` 中间层本身。

`DocumentBlock` 的价值是把不同文件格式统一成标准结构，使后续 chunk、trace、hierarchy、embedding、检索和位置回显能够复用同一条链路。真正的缺口在于：

```text
1. chunk 阶段没有充分消费 DocumentBlock 的结构字段；
2. parser 阶段没有根据 document_type 生成更高质量的 manual/laws block。
```

因此，推荐按两个阶段解决。

第一阶段，在 semantic chunk profile 中充分使用已有结构信号：

```text
heading/level
条款编号
章/节/条
步骤编号
Q/A 模式
table/image block
```

这一阶段不改变 parser 架构，主要目标是让 `general`、`manual`、`laws` 在当前 OpenRag 链路中真实生效。

第二阶段，让 `document_type` 可选进入 parser 层，尤其是 PDF parser：

```text
document_type = manual -> 生成更适合手册的 DocumentBlock
document_type = laws   -> 生成更适合法规条款的 DocumentBlock
```

这一阶段可以进一步对标 RAGFlow 的 parser 级能力，例如 manual/laws 专用 layout profile、章节识别、目录过滤和条款结构提取。

最终理想形态是：

```text
更高质量的 DocumentBlock
+
更合适的 semantic chunk profile
=
更接近 RAGFlow 的 manual/laws 分块效果
```
