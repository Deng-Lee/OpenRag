| 配置字段 | 无；使用 S02/S04 配置。 |

## R05-S06 让 Task、Broker、Worker 和 DocumentProcessor 绑定 Generation

| 项目 | 内容 |
|---|---|
| 步骤编号 | R05-S06 |
| 解决的问题 | 在线写任务仍可能按环境变量写固定 Collection，任务执行期间若 route 切换会跨 generation 混写，且任务归属不可审计。 |
| 实际采用方法 | Task 增加可空 FK；普通索引写任务在 Broker 行锁领取事务内绑定 active，显式 candidate 绑定保持不变；Worker 仅按任务 generation 解析一次 Runtime；Processor 在 Embedding 前和完成计数门禁再次核对指纹及 Chunk/Layer 物理名称；屏障仅过滤索引写任务。 |
| 修改文件 | `models/task.py`、`services/task_service.py`、`broker/task_broker.py`、两个 Task API、`worker/task_worker.py`、`processors/document_processor.py`、`indexing/runtime.py`、`20260715_0009_add_task_index_generation.py`、六组专项/回归测试、Schema 文档。 |

| 数据库字段 | `tasks.index_generation_id VARCHAR(36) NULL`，FK 指向 `index_generations.id`、`ON DELETE RESTRICT`，增加普通索引。可空仅用于 additive migration 和存量队列；索引写任务执行前不允许为空。 |
| 配置字段 | 无。 |
| 单元测试 | S06 绑定/屏障/Worker/SQLite migration：8 passed；相关既有任务、Worker、Processor、Runtime 回归：52 passed；全量：205 passed。 |

| 故障注入 | route 缺失时不领取未绑定索引写任务；任务无 generation、Runtime generation 不同、Chunk/Layer 名不一致、Embedding 指纹不一致均在写前失败；屏障开启时删除任务仍可领取。 |
| 数据准确性 | 已领取任务保留原 generation；route 后续变化不会改变任务字段或 Runtime；显式 candidate generation 不会被 Broker 覆盖为 active；重试保留原绑定。 |
| 性能影响 | 普通索引写任务领取时读取一条 global route；每任务读取一次 generation snapshot，Runtime 继续按 generation+fingerprint 缓存。 |
| 未解决问题 | Candidate 专用 `reindex_generation_file` 任务和文件级状态在 S08 实现；跨 generation 删除在 S09 实现；屏障 drain/激活并发协议在 S12 实现。 |
| 回滚方式 | 激活 versioned 写链路前可 downgrade 0009；已绑定任务存在时必须先停止 Worker 并确认不再依赖字段，不能直接删除 generation 记录。数据面紧急回退应切 route，不应恢复固定 Store。 |
| 退出门禁 | 通过。查询和在线写入均显式绑定 generation，Worker 不会在任务中途重新解析 active，灰度 Worker 无法通过固定 Collection 路径混写。 |

| 解决的问题 | 仅保留旧集合不能保证回滚后包含激活后的新增/更新/删除；previous 的模型可能不同，不能直接复制 active 向量；无 lag/RPO 的回滚会静默丢数据。 |
| 实际采用方法 | rollback_deadline 内，在线处理成功后按 previous generation Runtime 对最新规范源重新 Embedding，任务/文件状态绑定 previous；删除继续使用 S09 全版本传播；MirrorService 用规范源 hash、状态行和待物理删除行计算持久 lag；RollbackService 复用激活 advisory lock/write barrier/drain/CAS 协议，先验证 previous Provider/指纹/Store，再默认要求 lag=0，显式 accept_rpo 才允许带滞后反向切换。 |
| 修改文件 | `indexing/mirror_service.py`、`rollback_service.py`、Task/Broker/Worker、IndexGeneration 模型、管理 API/schema、`20260715_0015_add_generation_mirror_progress.py`、Schema 文档和专项测试。 |
| 新增函数/类 | 文档列出的 PreviousGenerationMirrorService 与 IndexRollbackService 核心函数；TaskType `mirror_previous_generation_file`；Worker previous mirror 分支；`POST /index-generations/rollback`。 |
| 数据库字段 | `mirror_lag_files BIGINT NOT NULL DEFAULT 0`、`last_mirrored_at TIMESTAMP` 及非负约束；复用 generation 文件状态推导 lag。 |
| 配置字段 | 无。镜像窗口使用 route.rollback_deadline；过期后不再创建新 mirror task。 |
| 单元测试 | Mirror/Rollback/Worker/Broker/API 直接影响 14 passed；覆盖新增、更新 hash、软删除、lag 清零、previous-only Runtime、零 lag 回滚、Provider 不可用、显式 RPO 和连续回滚 route_version 单调增长。 |
| 集成测试 | localhost PostgreSQL 迁移链 0008→0015 与逆向：1 passed。S12 真并发路由协议被回滚复用。 |
| 故障注入 | lag 非零且未接受 RPO、previous Provider/Collection 不可用、route_version 过期均在切换前失败且当前 active 不变；回滚后的原新 generation 只进入 retired，不自动删除。 |
| 数据准确性 | previous 使用自身指纹/模型重建最新源；删除待处理行计入 mirror lag，避免已软删但向量未清时误报 0；route 反向切换仍将 Chunk/Layer 作为同一 generation。 |
| 性能影响 | 在线成功后仅对变更 file 创建 previous task；全量 reconcile 会扫描规范源一次，避免逐文件 O(n²) lag 重算。保留窗口内存储与写放大约为双份。 |
| 未解决问题 | Mirror 调度为应用事件+显式 reconcile，不是数据库 CDC；进入回滚临界区前仍必须最终计算 lag。显式 accept_rpo 会把具体 lag 写入返回/审计语义，调用方必须外部审批。 |
| 回滚方式 | rollback 本身即受控反向切换；禁止手改 route/Alias。超过 rollback_deadline 后应停止镜像并按 S14 保留/清理流程处理 previous。 |
| 退出门禁 | 通过。回滚具备持久 lag、Provider 可用性检查、默认零 RPO 和显式风险接受，不再等同于“旧集合存在”。 |

| 退出门禁 | **代码门禁通过，生产 RBAC 门禁未通过**。退休数据具备显式安全清理路径，但生产 runtime“无法 DropCollection”尚待真实权限验证。 |
